## Findings and acceptance tests

1. **High — lost configuration prevents fail-safe local disconnect.** `lib/gmail-server.ts:212` calls `oauthConfig(req)` before the revocation try/catch and local purge. Reproduction: create a synthetic credential for A; remove `TOKEN_ENCRYPTION_KEY`; POST `gmail/disconnect`. Observed 503 and credential count remains 1. Jobs/plans similarly never reach cancellation. Configuration/key loss is a realistic incident recovery condition. Fix: try optional configuration/decrypt/provider revocation within a bounded guarded block; always erase the local credential, cancel jobs/plans and remove OAuth transactions atomically; clearly report that remote revocation was not confirmed and direct the user to Google connections. Retest: missing key/client secret, invalid envelope, provider revoke timeout, repeat disconnect, concurrent refresh and reconnect. **Retest UNVERIFIED.**

2. **High — restore/deletion protection is documented but lacks software.** `docs/disaster-recovery.md` describes encrypted snapshots and authoritative tombstone replay; only a `tenants.deleted` flag in the same database exists. Searches of scripts/runtime/schema find no snapshot, restore validator, independent deletion journal or restore preflight. Restoring an older snapshot can resurrect deleted tenants and old actionable plans unless an operator manually follows the draft. Fix: an encrypted, versioned snapshot tool with separate authoritative deletion manifest, integrity checks, fail-closed restore, tombstone replay and cancellation of queued/executing plans. Never automatically replay mailbox mutations. Acceptance: synthetic A/B snapshot, delete A, isolated restore + replay leaves A denied and B intact; wrong key/tamper/version reject before writes; all old plans/jobs disabled. A real D1 recovery drill and backup custody/retention are separately external verification blockers. **Retest UNVERIFIED.**

3. **Medium — privacy export omits most stored personal data.** `app/api/[...path]/route.ts:480` returns only settings and up to 100 rules through `state()`. Stored Gmail metadata, action history, inventory, plans and jobs are absent; accounts with more than 100 rules are silently truncated. Synthetic reproduction: seed inventory, POST export, result keys exactly `rules,settings` while inventory exists. Fix: explicit bounded paginated export for every personal data collection, tenant scoped, stable cursor and snapshot/version semantics; exclude credential ciphertext/tokens and PKCE state/verifier. Acceptance: >100 rules and >50 actions, multiple metadata pages, tenant B IDs excluded, complete deduplicated export, secrets absent and no-store headers. **Retest UNVERIFIED.**

4. **Medium — safe manual unsubscribe exists only as an adapter and generic error.** `packages/integrations/unsubscribe.ts` safely declines automatic requests, but `app/api/[...path]/route.ts:273` immediately returns generic 409 for Gmail; live UI confirmation at `app/page.tsx:1756` tells the user to use Gmail yet still offers “Confirm unsubscribe”. There is no destination assessment/Gmail message link. Fix: read tenant-owned unsubscribe metadata, return structured manual/blocked/unavailable assessment; show actual destination hostname and warning, plus a fixed-origin Gmail link/instructions; never auto-follow or fetch email-supplied URLs. Acceptance: malicious/local/credential URLs blocked, unsupported cases clear, no network request to any supplied target, correct message linked, synthetic demo remains clearly labeled. **Retest UNVERIFIED.**

5. **Medium — retention and actionable incident telemetry are missing implementation.** `docs/retention.md` accurately says proposed policy. Expired OAuth transactions/previews and historical records have no purge job. API telemetry at `app/api/[...path]/route.ts:526` contains only event/type; handled provider failures, lease age, partial actions and purge lag are not monitored. `health` always returns `status:ok` with fixed provider/scheduling text if SELECT 1 succeeds; it is a database liveness probe, not readiness. Fix: bounded retention sweeps that preserve uncertain action reconciliation/Undo limits and tombstones; privacy-safe typed operation events; separate liveness from authenticated operational readiness. Acceptance: simulated time proves expired purge and preservation, no token/email/subject/URL in captured logs, synthetic failures expose only opaque IDs/outcomes; external alert delivery and operator ownership remain separate blockers. **Retest UNVERIFIED.**

6. **Medium — AI consent disclosure and route-level evidence incomplete.** Smart Mode description promises explicit metadata analysis (`app/page.tsx:1479`), yet `assistant` automatically sends each user command to OpenAI when Smart Mode is enabled (`app/api/[...path]/route.ts:384`). Per-message analysis does require both Smart Mode and `approved:true`, and sends sender/subject/labels only. Clarify the distinction: disclose command sharing on assistant submission and the exact metadata fields/recipient before analysis. `store:false` is not a retention guarantee. Existing adapter tests cover injection in subject, strict schema and refusals, but backend harness stubs AI and has no no-consent request capture or route policy conflict assertion. Acceptance: provider capture is empty in Privacy Mode/without message approval, approved Smart Mode sends only declared bounded fields, revoked consent prevents new requests, timeout/refusal/malformed JSON remain advisory and cannot create actions, model trash recommendation cannot bypass deterministic protection. **Retest UNVERIFIED.**

7. **High launch gate — deployed identity trust boundary is unverified.** `app/chatgpt-auth.ts:21` accepts `oai-authenticated-user-id/email` headers; `build/sites-worker.ts:26` forwards the Request unchanged. Local plugin strips forged headers and substitutes a synthetic identity, but is absent in production. This may be correct with a trustworthy Sites gateway; source alone cannot establish that outside clients cannot inject these headers or reach the Worker directly. Do not describe this as an established remote vulnerability without exercising ingress. Acceptance: on the authorized deployed gateway, anonymous and forged-header requests denied, signed-in A cannot retrieve B, direct origin unavailable or authenticated, correct audience verified. Obtain platform contract/evidence rather than inventing an application signature scheme incompatible with Sites. **UNVERIFIED external deployment boundary.**

## Existing positive boundaries

API error logging omits exception message and provider bodies. JSON responses use no-store/nosniff/no-referrer. OAuth state atomically consumes a tenant-bound unexpired transaction; adapter tests exercise PKCE and authenticated encryption substitution/tampering. Account deletion removes tenant-owned current records and rejects silent recreation. AI adapters expose no tools, bound metadata/output and validate strict schemas; message analysis returns deterministic policy separately rather than applying AI advice. Unsubscribe adapter never performs arbitrary fetch or sends mail. These are local evidence, not provider approval or operational readiness.
